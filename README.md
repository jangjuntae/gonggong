# 공공 정책금융 신청·심사·사후관리 시스템

복잡한 자격조건과 심사 절차를 가진 공공서비스를 안정적으로 처리하기 위한 웹 기반 정책금융 정보시스템입니다.

고객의 금융상품 신청부터 자격검증, 담당자 심사, 대출 실행, 상환 및 연체관리까지 전체 업무 흐름을 관리합니다.

## 프로젝트 목표

- 금융거래의 정확성과 데이터 정합성 보장
- 역할과 담당 부서에 따른 개인정보 접근통제
- 신청·심사·거래의 전체 처리 이력 추적
- 멱등성 처리를 통한 중복거래 방지
- 장애와 부분 실패에 안전한 트랜잭션 설계
- 대량 데이터 환경에서의 조회 성능 개선

## 주요 사용자

| 사용자 | 주요 기능 |
|---|---|
| 고객 | 상품 조회, 신청서 제출, 증빙서류 등록, 진행 상태 및 상환 내역 조회 |
| 심사 담당자 | 신청 조회, 자격검증 확인, 서류 검토, 보완 요청, 승인·거절 |
| 사후관리 담당자 | 대출 실행 내역, 상환 현황, 연체 대상 및 이상거래 관리 |
| 관리자 | 상품, 자격조건, 사용자, 부서 및 권한 관리 |
| 감사 담당자 | 개인정보 조회, 상태 변경, 심사 및 금융거래 처리 이력 확인 |

## 핵심 업무 흐름

```text
상품 조회
  → 신청서 작성 및 접수
  → 자격조건 자동검증
  → 담당자 배정 및 서류심사
  → 승인 또는 거절
  → 대출 실행
  → 상환계획 생성
  → 상환 처리
  → 연체 및 사후관리
  → 계약 종료
```

## 핵심 기능

### 상품 및 자격조건 관리

- 지원 대상, 연령, 소득, 신용점수, 지역 및 한도 조건 관리
- 자격조건을 코드가 아닌 데이터베이스에서 관리
- 정책 변경 전 심사 근거를 보존하는 규칙 버전 관리

### 신청 및 심사

- 신청서와 증빙서류 검증
- 상품별 자격조건 자동검사
- 중복신청 확인 및 미충족 사유 제공
- 담당자 배정, 보완 요청, 승인·거절
- 허용된 신청 상태 전이만 처리

### 대출 및 상환

- 승인된 신청만 대출로 실행
- 대출계약, 거래원장, 신청 상태, 상환계획을 하나의 트랜잭션으로 처리
- 원리금균등상환 우선 구현
- 금액 계산에 `BigDecimal` 사용

### 거래 안정성

- 요청별 멱등성 키 발급
- 거래 고유키에 `UNIQUE` 제약조건 적용
- 동일 요청의 처리 결과 재사용
- 부분 실패 발생 시 전체 작업 롤백

### 개인정보보호 및 감사

- 역할 및 담당 부서 기반 접근통제
- 전화번호와 계좌번호 마스킹
- 민감정보 암호화와 비밀번호 해시 저장
- 개인정보 조회 및 주요 정보 변경 이력 기록
- 실제 개인정보 대신 가상 데이터 사용

### 연체 및 이상행위 관리

- 납부기한 경과와 연체 일수 계산
- 연체 대상 목록과 담당자 알림
- 반복 신청, 중복 상환 및 비정상 개인정보 조회 탐지
- 탐지 규칙과 판단 근거 제공

## 기술 스택

| 영역 | 기술 |
|---|---|
| Backend | Java, Spring Boot, Spring Security, Spring Data JPA |
| Database | PostgreSQL |
| Frontend | Thymeleaf |
| Test | JUnit |
| API 문서 | Swagger / OpenAPI |
| 운영 | Docker, Spring Actuator, 구조화 로그 |
| 협업 및 자동화 | GitHub, GitHub Actions |

초기에는 단일 애플리케이션 구조에서 트랜잭션, 데이터베이스, 보안 및 테스트를 정확히 구현하는 데 집중합니다.

## 주요 데이터 모델

- 사용자·권한: `CUSTOMER`, `EMPLOYEE`, `DEPARTMENT`, `ROLE`, `PERMISSION`
- 상품·규칙: `FINANCIAL_PRODUCT`, `PRODUCT_RULE_VERSION`, `ELIGIBILITY_RULE`
- 신청·심사: `APPLICATION`, `APPLICATION_DOCUMENT`, `SCREENING_RESULT`, `STATUS_HISTORY`
- 대출·상환: `LOAN`, `REPAYMENT_SCHEDULE`, `FINANCIAL_TRANSACTION`, `OVERDUE`
- 감사·안전: `AUDIT_LOG`, `RISK_ALERT`, `IDEMPOTENCY_REQUEST`

## 데이터베이스 설계 원칙

- `PK`, `FK`, `UNIQUE`, `CHECK` 제약조건 적용
- 거래 데이터의 임의 삭제 금지 및 필요 시 논리 삭제
- 거래원장과 현재 잔액 분리
- 중요 정보의 변경 이력 보존
- 신청 당시 정책 버전과 심사 결과 보존

## 성능 테스트 계획

- 고객 10만 명
- 신청 20만 건
- 대출 10만 건

- 감사로그 100만 건 이상

실행계획을 분석하고 복합 인덱스를 설계한 뒤 동일한 조건으로 개선 전후 성능을 비교합니다.
