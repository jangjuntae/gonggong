# 테스트 전략

## 테스트 계층

| 종류 | 범위 | 주요 검증 |
|---|---|---|
| 단위 테스트 | 상태 머신, 규칙, 계산기 | 경계값·분기·반올림 |
| Repository 테스트 | PostgreSQL 제약·쿼리 | FK/UNIQUE/CHECK, 인덱스 사용 가능성 |
| Service 통합 테스트 | 유스케이스와 트랜잭션 | 원자성, 롤백, 동시성 |
| API 테스트 | 계약·Validation·오류 | 상태 코드, DTO, 인증 |
| 권한 테스트 | 역할×부서×소유권 | 허용/거부 및 정보 최소화 |
| 성능 테스트 | 기준 데이터와 쿼리 | 처리량, 지연, 실행계획 |

Repository·통합 테스트는 PostgreSQL과 동작 차이를 줄이기 위해 Testcontainers 사용을 우선 검토한다. H2만으로 DB 고유 제약을 검증하지 않는다.

## 최우선 시나리오

> 동일 상환 요청이 동시에 두 번 들어와도 거래원장과 잔액에는 한 번만 반영되어야 한다.

- 대출 실행 중 마지막 단계가 실패하면 계약·원장·상태·계획이 모두 롤백된다.
- 허용 목록에 없는 신청 상태 전이는 모두 실패하고 이력이 왜곡되지 않는다.
- 서로 다른 키의 동시 상환에서도 Lost Update가 발생하지 않는다.
- 신청 시점 규칙 버전은 상품 정책 변경 후에도 동일한 결과 근거를 유지한다.
- 권한 없는 다른 부서 직원은 개인정보를 볼 수 없고 거부 사실이 기록된다.
- 원리금 합계, 마지막 회차 오차와 0·최대 금액 경계를 정확히 계산한다.

## 테스트 설계 원칙

- Given-When-Then으로 업무 의도를 드러낸다.
- 시간·UUID·외부 연동은 주입 가능하게 설계해 결정적 테스트를 만든다.
- 금융 계산은 예제 기반과 속성 기반 테스트를 함께 검토한다.
- 동시성 테스트는 동시 시작 장벽을 사용하며 반복 실행한다.
- 실제 개인정보나 운영 덤프를 사용하지 않는다.
